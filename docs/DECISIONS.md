# Decisions, pins and verification log

## About this record

zab is developed by Andrew V. Sutherland in a private repository, with coding agents doing much of the implementation and review (CONTRIBUTING.md). The entries below were written as the work went, and use its shorthand:

- **Drew**, and **the SPEC owner:** the maintainer, Andrew V. Sutherland.
- **The PM:** the coding agent that coordinated the work. **A** and **B:** the two coding agents that implemented the early releases. **The developer of #NNN:** the coding agent that implemented that issue.
- **The development machine:** the machine from which the end-to-end suites are run against test VMs, and Claude Code's live tests were run; Codex never runs there. **The Codex development machine:** where Codex's live tests were run.
- **#NNN:** an issue or pull request of the private repository; a **comment** number is a comment there. **PR n**, without `#`: a step of `docs/ADMIN.md`'s plan for the admin server (§8.3), not a pull request number.
- **A report name**, such as `20261023T165936Z-96dfe435`: the report of an end-to-end run (a test VM's suite, or the admin suite on the rig), named after the run's start (UTC) and the commit it tested.
- **The rig:** the test infrastructure that the end-to-end suites use: a test admin server, test VMs and a test participant, all test resources (ADMIN §7).
- **Mn** and **AT-n:** the first releases' milestones and acceptance tests (SPEC §16, §17).
- **Qn**, **Vn** and **An:** ADMIN.md's questions (§10), verification items (§9) and admin end-to-end scenarios (§7). **Scenario n:** an end-to-end scenario of `tests/e2e/`.
- **P-n:** an admin bot's plan (ADMIN §2.4); **P-a:** a later item of ADMIN §8.3's plan. **On:** a step of the runbook that moved the first workshop's fleet to the admin server, which ADMIN §8.4 held up to v0.2.15; the entries cite **O5**, the join (`join_server.py` moved the VMs to the deployer's dedicated key, then added the server's key), and **O6**, the bots' move to `zab-provisioner` (`move_bots.py`). ADMIN §8.4 now keeps the tools.

Append to this file; do not rewrite history. To change a decision, add a new decision that supersedes the old one, and mark the old one *superseded by Dn*. A redaction for publication, which changes no decision, result or date, is recorded the same way: by a dated entry at the end.

### 2026-10-11: The fork boundary (SPEC §8.8; issue #202, PM on #227)

A fork copies the parent's history through its last turn that is **no longer running**. A turn a bridge restart or `!stop` interrupted has ended, and it is included:

- it is exactly the conversation the parent's own next turn resumes from (Claude Code closes the open tool call as "interrupted" on resume);
- the fork's files come from `fork_base`, the parent's working tree, which already holds that turn's edits, so keeping the turn explains them;
- #212's "excluding any unfinished turn" means one still running, as in Codex's `lastTurnId … cannot be in progress`.

After a restart, recovery kills any surviving Claude process that isn't the bridge's own child, so a reopened session that isn't busy has nothing running. The Claude copy is cut at the transcript size recorded when the running turn started, or taken whole when the session is idle, and a half-written last line is always cut. Decided by the PM after two Codex rounds asked for an explicitly completed offset instead.

### 2026-10-23: `!fork` in the core (SPEC §7.11; issue #202)

| Decision | Why |
|---|---|
| The fork is created in the bot's message handler, as `!new` and `!attach` are, not in the parent's actor | The parent's actor keeps handling its running turn's events meanwhile; a worktree and a native fork take seconds, plus the worktree post-create hook (`lean-project --repair-all` on the fleet, up to 60 s), as for `!new`. Ordinary topics keep the configured default. |

### 2026-10-13: rendered pages on the file server (issue #256)

**Server-side rendering.** `workshop/files/render.py` renders Markdown with markdown-it-py 4.2.0 and mdit-py-plugins 0.6.1, and highlights source with Pygments 2.21.0:
- Markdown gets the `gfm-like` preset (tables, strikethrough, autolinks via linkify-it-py), plus task lists, footnotes, GitHub-style heading anchors, and `$…$`, `$$…$$` and ```` ```math ```` math.
- Math stays as TeX in `.math` elements. KaTeX typesets it in the browser.
- **KaTeX is vendored:** 0.19.0, MIT, from the npm tarball checked against its sha512 integrity, keeping only `katex.min.js`, `katex.min.css`, the `woff2` fonts and `LICENSE`, under `workshop/files/static/katex/`. The server serves it, so a page never depends on a CDN.

**Why server-side:** the alternative was JavaScript renderers in the browser. Server-side keeps the sandboxed pages nearly script-free (only KaTeX, and only on pages with math), keeps the extension-to-language map and the GP and Magma grammars in one tested Python module, and needs no JavaScript highlighter with grammars for Lean, GP and Magma.

**Dependencies:** these libraries are the file server's only. They're pinned with hashes in `workshop/files/requirements.txt` for its venv, and in the dev dependency group for the offline tests. **The zab wheel's runtime dependencies are unchanged.**

**GP and Magma:** Pygments ships neither. `workshop/files/lexers.py` holds two small `RegexLexer`s written for this repository from the languages' documentation: GP's control statements and comment, metacommand and string syntax, and Magma's reserved-word list. No grammar or keyword list was copied from an editor mode or a Jupyter kernel, so no third-party license applies. `.m` is Magma, never MATLAB or Objective-C; `.sage` uses the Python grammar.

**Raw HTML in Markdown is escaped, never passed through.** That's the strictest sanitizer, and it needs no HTML-sanitizing library. `<details>` and the like show as text; an allowlist can come later if wanted.

**Caps:** a file is served as plain text, as before, when it isn't UTF-8, has over 20 000 lines, or is over 1 MB (a source file) or 200 KB (Markdown). Markdown with over 60 000 block-level tokens also stays plain text, which mostly means very large tables. `?raw=1` always returns the exact bytes.
- **Why Markdown's caps are lower:** its worst inputs cost up to about 5 µs a byte, a table holds about 1 KB of tokens per byte, and two of its rules are quadratic. Under 1 MB, a task list took 17.6 s and a table 635 MB (review on #265). At these caps, every worst case measured on the development machine either renders or falls back to plain text within 1.1 s and +94 MB. #265 records the timings. Highlighting a source file is linear: 1 MB takes about 1–2 s.
- **Two plugins are replaced.** render.py has its own one-pass rules for task lists and heading ids. The plugins searched back for each item's list, and counted each repeated heading's `-n` from 1.
  - **Heading ids** are the plugin's: no differences in 20 000 random documents.
  - **Task lists** match the plugin's output in 180 000 random documents, except in one case: a tab, newline, CR, VT or FF after `[ ]` or `[x]` instead of a space. The plugin then drops the marker and draws no checkbox, because it builds one only after a space. render.py draws it, as GFM does: a task marker may be followed by any whitespace. This is a deliberate difference (reviewer's fuzz after #265).
  - **Tests** check that the output matches the plugins' outside that case, and that the case gets its checkbox.
- **Warm-up:** loading render.py loads every lexer and rule it uses. Pygments' lazy `pygments.formatters` loader isn't thread-safe, and a fresh server's concurrent first renders failed with ImportError.

### 2026-10-15: the export check parses participants' bytes in the admin service (accepted risk; #360; closed by #374)

**Decision (on the approval of #360).** `collect_exports.py` checks each archive with `archive_check.py`. That checker runs Python's `gzip` and `tarfile`, GNU tar and gzip(1) on bytes the participant controls, in a child of the `zab-admin` service. That service can read the fleet's SSH key and reach AWS through the instance role. Since the re-pack (below), GNU tar and gzip(1) no longer read them; Python's `gzip` (zlib) and `tarfile` still do, in that child, until #374's sandboxed unit lands.

- **What bounds it.** The child limits itself before it reads a byte: `RLIMIT_AS` 256 MiB, `RLIMIT_CPU` 600 s, no file written, 32 files, no environment, cwd `/`. It reads its input read-only. The parent adds a wall-clock timeout and keeps only an exact `ok`. These bound the check's cost and make every failure refuse the archive.
- **What doesn't.** The limits are not containment. A memory-corruption bug in the C parsers (GNU tar's header and PAX code, for example CVE-2022-48303 and CVE-2023-39804; gzip's or zlib's inflate) would run with the service's access. Stock, patched Ubuntu 24.04 packages make that unlikely, not impossible.
- **Accepted until the sandboxed checker lands:** a unit without network or key access, such as `systemd-run` with `PrivateNetwork=yes` and `InaccessiblePaths=` on the state directory, tracked in #374. It must land before the first real `!export`, on Nov 1, after the workshop of Oct 31.
- **Closed by #374.** The re-pack runs in `zab-archive-check@.service`, an instance per connection to a root:zab-admin socket, as a dynamic user of its own, with no network and no socket (neither `socket()` nor io_uring, which the review of #384 found reaching D-Bus and DNS until `@aio` was denied), `InaccessiblePaths=` on `/etc/zab-admin`, `/var/lib/zab-admin` and the sockets under `/run` that others may reach (not `/run/systemd` as a whole, which PID 1 needs: A19, #392), nothing writable, a system call filter, and memory, CPU and time limits (ADMIN §1.2). `collect_exports.py` hands it the archive as a read-only descriptor and parses none of it: no process that holds a key reads participants' bytes any more. What remains: the stored archive's claim holds as long as the checker runs its own code; code run in it (a parser exploit) can answer any bytes as the re-pack, stored unexamined, which go back to the participant who controls the input anyway.

### 2026-10-15: exports are re-packed; only our own writer's archive is stored (#374)

**Decision (#374).** #360's check refused crafted archives one case at a time, about ten rounds of them, and one gap of that class remained: GNU tar's reading of link types and targets was never compared with `tarfile`'s. So the check now re-packs instead (`archive_check.py`, `Repack`). It reads the participant's archive with `tarfile`, under all of #360's rules and refusals, and writes a new gzip tar from what it approved:

- regular files, and a copy of the earlier regular file for each hard link (refused when there is none); directories, under normalized names;
- modes 0644 or 0755 (0755 for directories), owner and group 0 and unnamed, GNU format, no PAX attributes, devices or extended attributes;
- no symlinks: `SYMLINKS.txt`, a name no member may take, lists their names and targets so that participants can recreate them. Devices and FIFOs are left out;
- **names Windows can take** (the review of #383: rename, don't refuse or scope the claim, since participants may extract on Windows). Each component's characters Windows forbids, `%` itself and trailing dots or spaces become `%XX`, and a device name's first letter too; a component that would then pass 255 bytes (Codex on #383) is cut short and ends with `%~` and 32 hex digits of the original's SHA-256. That is deterministic and, `%` being renamed and `%~` found in no other component, injective but for a 128-bit hash collision: no rename makes two members one. `RENAMED.txt`, also reserved, lists the original and the new name of each. The claim then covers Linux, macOS and Windows: nothing outside the directory, and no **file** at a credential's path (extraction also makes the directories a name implies).

`collect_exports.py` stores only that new archive and always deletes the participant's. What is stored is exactly what our writer produced, so no other parser's reading matters any more, and GNU tar no longer runs on the participant's bytes. The re-pack reads the archive twice: the headers first, so that a refused archive yields no output, then everything, writing as it goes. It is bounded like the check: at most `--max-expanded-mb` read, at most that much written, copies included, and at most that much decompressed again for the copies; at most 100,000 hard links and 16 MiB of their targets (held from the first pass), 8 MiB of symlink and renamed names counted before escaping (up to four times that held), and 256 components per name, since `_through` costs their square (a 1.3 KB gzip of ten 30,000-component names took 37.9 s of CPU). Every refusal is framed, a `MemoryError` or any other exception included. It compresses at gzip level 3, which on text is about twice as fast as the default 6 for about 6% more bytes; 1 GiB of small files re-packs in about 12 s of CPU on the development machine.

### 2026-10-19: the admin server's status reads are not logins (#507)

**Decision (the developer of #507).** `status.py` reads a VM as `zab-monitor`, P-a's user (ADMIN §8.3), and idle stop leaves that user's SSH sessions without a terminal out of its logins (`idle_stop.py`, module doc; ADMIN §4.1). `push_config.py --idle-stop N` sets it up, after the timer; `--idle-stop 0` removes it.

- **A session of that user is the read and nothing else.** Its login shell is the read (`/usr/local/lib/zab/status_read_login`, which runs `/usr/bin/sudo -n -H -u agent /usr/local/lib/zab/status_read.sh` and ignores what it is asked), so every way in runs the read, EC2 Instance Connect's keys too (the review of #514). Its `authorized_keys`, in a home and `.ssh` that are root's, holds only `restrict` lines with that command forced: no terminal, forwarding or `~/.ssh/rc`. Only an Instance Connect key may also forward ports and sockets, and use sftp where sshd serves it itself (`internal-sftp`), as it may for `ubuntu`. The read's agent side is agent's own login shell (`.profile`) and `zab`, as `STATUS_CMD`'s always was, and status.py's 180 s timeout ends the session. `/etc/sudoers.d/zab-monitor` lets it run that one root-owned script as `agent`, without arguments, and nothing else. sshd names a session after the user it authenticated, so no one else's session carries the name. Idle stop ignores exactly `zab-monitor@notty`: a terminal of that user would count.
- **Its keys are ubuntu's,** each plain key line (a line with options, such as `from=`, is left out), copied by idle stop on every tick. Whoever may log in as `ubuntu` may read: the server, the deployers' break-glass keys, the rig. Nothing has to pass the server's public key, and a key that `join_server.py --remove` takes from ubuntu stops reading at the next tick. ubuntu's file is read as root with care: neither `.ssh` nor the file through a symlink, both ubuntu's, so that no link or hard link points the read at another file; no FIFO or device; at most 64 KiB. Otherwise no key reads until it is sane again.
- **What it doesn't claim.** Whoever logs in to a VM is root there (`ubuntu`; `agent` has passwordless sudo, D22), and root can make a `zab-monitor` session anything, or stop idle stop outright. The exemption makes no session a read by accident; it can't stop root.
- **The fallback.** Where the user can't log in, or its read fails on the VM, `status.py` reads as `ubuntu` as before, a login. A timeout, or a VM that SSH can't reach, gets no second try.
- **Rejected:** a marker that the read writes (any `ubuntu` session can write one, and one left by a killed read hides a later session that gets its PID); recognising the read by its processes (a multiplexed connection's channels share one sshd process); counting only sessions seen at two ticks (a short `ssh vm 'nohup job &'` would no longer count); a forced command on ubuntu's own line for the server's key (push_config needs that key unrestricted, from the same address, and sshd takes the first line for a key whose options let it in); `AuthorizedKeysCommand` or a `Match User` block in `sshd_config` (an sshd change on every VM, where a mistake locks everyone out); only the server's key in the user's file (every rollout would need its public key, and removing it from ubuntu's would leave it there).

### 2026-11-01: `!btw` side questions (SPEC §7.13, §9.10; issue #716)

| Decision | Why |
|---|---|
| A new contract hook, `Backend.side_question(native_id, question, *, timeout_s) -> str`, behind `Capabilities.side_question` (default false) | As `fork_session` is: a backend answers only once its behaviour is verified, and the core never calls an absent hook. The backend frames the question, since what each can drop differs (Claude its tools, Codex only down to a read-only sandbox). |
| It runs as a task of the bot's bridge, never in the session's actor; no turn slot | The actor's loop is serialized: a side question there would hold up the running turn's events, and in the message handler it would hold up `!stop` and the bot's other messages for up to its timeout. A side answer must not wait behind turns (#716 AC 5). |
| One side question per session at a time; a second **waits**, with ⏳ | The issue lets the PR choose. Waiting loses nothing the user sent, and each answer takes seconds; a refusal would ask them to resend. The lock is in memory: a restart drops what waits, like the one in flight. |
| 120 s for the backend | A side answer is one model reply with no tools, a few seconds to a minute on a long conversation; 120 s leaves room for a long resumed context and high effort. Then the backend stops what it started (Claude: the §9.6 sequence; it may hold the OAuth refresh lock, so never a plain SIGKILL). |
| A `!btw` replayed before its session's reopen waits up to 120 s for it | The message that woke an idle-stopped VM is replayed before the backends are up; refusing it would ask for a retry the user can't see the need for. A fork waits durably (`pending_forks`); a side question is not worth persisting. |
| The marker `💬 [btw](<link to the !btw message>):` on **every** part | Zulip has no threads: the link ties the answer to its question in a busy topic. Every part carries it, so that peer context (`CONTROL`) leaves out a long answer's later parts too; the renderer is told the marker's length, so parts still fit. |
| The mention in the first part's marker when the answer took at least 60 s, whatever `mention_after_s` says | The issue exempts a fast answer from the long-turn mention (#711): its asker is waiting for it. A slow one gets the mention so that the topic shows the **@**; it goes in the answer, not a separate line, so peer context's marker covers it. Not tied to `mention_after_s`: a side question never runs past its 120 s, the setting's default, so the first version's "at least `mention_after_s`" never fired; the review's "at least `min(mention_after_s, 60)`, never under 60" comes to the same 60 s (review of #737). |
| Rendered as a final answer, with no snapshot and no turn files | "Links included" (AC 6), but "no snapshot" (AC 4): references link to GitHub permalinks, uploads or *(local)* as outside a turn (§11.3). |
| Claude resumes the live session, not a cut copy | Verified (above, 2026-11-01): it reads the running turn's progress safely, a half-written last line included, and saves nothing; a copy would add I/O and hide the progress `/btw` shows. |
| `zab history` and peer context leave out every side question and every part of a side answer, whoever sent it (`peer_context.side_message`) | "Kept out of every history" (AC 4) covers an agent reading another topic too, and another participant's side questions as much as the user's own (review of #737 and codex round 1 on it). A page of `zab history` may then show fewer than `--limit` messages. |
| The `!btw` message's `inbound` row becomes `side_question`, its `handled_at` the time its answer starts | Idle stop counts a message whose disposition isn't `ignored` (`LAST_ACTIVITY_SQL`); a side question left `ignored` let a VM power off in the middle of its answer (review of #737). |
